Що має бути в проєкті?

1. Inference-сервіс

FastAPI‑код в app/main.py, модель завантажується при старті;
Є окрема функція predict(data) — повертає передбачення;
Виклик детектора дрейфу (опціонально — async/optional).
2. Drift-детектор

Використай один із варіантів:
Great Expectations з eval передбачень;
Alibi Detect з попередньо натренованим drift-детектором;
У разі дрейфу — логування (print("Drift detected")) або виклик Webhook.
3. CI для retrain

У .gitlab-ci.yml описаний job retrain-model:
- Запускає скрипт тренування (може бути мок);

- Генерує нову модель;

- Збирає новий Docker‑образ;

- Оновлює Helm‑чарт або пушить нову версію в гілку;

Job може запускатись вручну або через webhook із сервісу.
4. Helm + ArgoCD

У helm/ — стандартний Helm‑чарт;
У argocd/ — application.yaml з auto-sync;
ArgoCD під'єднано до Git‑репозиторію з чартом.
5. Моніторинг і логування

Prometheus scrape конфіг для сервісу або подів;
Loki + Promtail збирає stdout;
У Grafana — дешборд з основними метриками:
- Запити/хв

- Latency

- Drift alerts (кількість або подія)



Виконайте перевірку:

kubectl port-forward показує працюючий API
Відповіді містять ознаку прогнозу + логуються
Drift повідомлення видно в логах (kubectl logs)
Grafana показує трафік
GitLab CI запускає retrain
ArgoCD підтягує оновлений Helm‑чарт

Результат виконання

У кластері працює FastAPI‑сервіс, задеплоєний через ArgoCD;
Його Helm‑чарт налаштований на логування в Loki та збір метрик;
При кожному запиті:
- вхідні дані логуються,

- модель обчислює відповідь,

- відбувається перевірка на аномалії/дрейф;

Якщо спрацьовує drift_detector, запускається GitLab CI пайплайн retrain-model;
Результатом retrain є:
- новий артефакт моделі,

- нова версія Docker‑образу,

- оновлений Helm‑деплой (або auto-sync через ArgoCD);

У Grafana можна побачити:
- метрики завантаженості сервісу,

- кількість спрацювань детектора дрейфу,

- час відповіді моделі;

У README.md детально описано, що зроблено, як перевірити, і як оновити модель.
